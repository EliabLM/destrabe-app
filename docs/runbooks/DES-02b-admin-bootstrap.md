# PROPUESTA — bootstrap manual del primer ADMIN (NO ejecutar en este PR)

**Estado: pendiente de aprobación y ejecución humana posterior.** No hay endpoint, script público ni usuario ADMIN predefinido. Prohibido usar cuentas ajenas, entornos reales sin autorización y contraseñas/códigos en logs o tickets.

1. Dos humanos autorizados (solicitante y aprobador independientes) registran motivo, alcance, identidad esperada del primer ADMIN, entorno y ventana de mantenimiento aprobada. Verifican identidad del titular por canal independiente y que él mismo completó OTP y ya tiene usuario CLIENT; no usan el teléfono como única evidencia administrativa.
2. Acceso a DB restringido, temporal y auditable, sin compartir credenciales; congelar cambios de rol e invitaciones durante la ventana. Hacer backup consistente y probar restauración en entorno aislado; documentar identificador de backup y aprobación, nunca secreto. Consultar `User` por **id obtenido por procedimiento controlado**, confirmar identidad/`phoneNumberVerified`, rol CLIENT y ausencia de cambios concurrentes; no volcar PII a logs.
3. En transacción con bloqueo de la fila identificada, revalidar condiciones anteriores, ejecutar UPDATE condicional **solo para ese id si role=CLIENT y phoneNumberVerified=true**, verificar exactamente una fila afectada y que el rol resultante es ADMIN; el segundo humano coteja antes de COMMIT. Si no se cumple una condición o cambia la identidad, ROLLBACK y escalar: nunca ampliar el WHERE ni crear un usuario nuevo. Registrar actor ejecutor, aprobador, hora, motivo, id de usuario y resultado en bitácora operativa protegida sin secreto OTP.
4. Tras commit, comprobar por lectura controlada rol ADMIN del mismo id y que no se elevaron otros usuarios (comparación antes/después del snapshot de roles), revocar acceso temporal DB. Probar emisión solo en entorno autorizado después de aprobar el despliegue separadamente; jamás usar token real en PR/issues.
5. Plan de reversión: si la elevación fue errónea, congelar emisiones y canjes; revisar/revocar invitaciones emitidas por ese ADMIN, respaldar evidencia de auditoría, en nueva transacción autorizada y con doble control cambiar ADMIN→CLIENT **solo si sigue siendo el mismo id y no tiene obligaciones administrativas pendientes**; comprobar la fila y otras cuentas, registrar incidente. Restaurar backup si hay corrupción más amplia conforme runbook operativo aprobado.

El rollback de esquema (`DES-02b-rollback.sql`) elimina invitaciones y auditoría: requiere exportar evidencia y retirar primero rutas desplegadas; ensayo de rollback en CI no elimina datos persistentes. La propuesta no autoriza ejecución ni sustituye aprobación humana.
