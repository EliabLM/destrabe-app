# DES-03 — Diseño propuesto: datos, rollout y rollback

**Solo diseño, NO migración ejecutada.** Depende del [delta spec](../../specs/DES-03-reconciliacion-mp/spec.md) y del gate humano allí. En `main@b07282b` `Payment.mpPaymentId String? @unique` almacena `Preference.create().id`, y la ruta de init y webhook escriben el mismo campo. `Payment.amount` es `Float`; `OperatorProfile.mpAccountId` es nullable. Lockfile y backend declaran `mercadopago` 3.2.0. No tocar DES-02 (listado/onboarding).

## Modelo candidato, sujeto a aprobación

- `Payment.mpPreferenceId String? @unique`: ID de preferencia Checkout Pro **actual**, exclusivamente. `Payment.mpActualPaymentId String? @unique`: ID del recurso Payment consultado, exclusivamente; puede ser null mientras PENDING. Conservar inicialmente `mpPaymentId` legado, **no volver a usarlo para asociar webhooks**. `Payment.expectedCurrency String?` y `Payment.expectedCollectorId String?` son snapshots del init para compararlos con `Payment.get`; requeridos lógicamente para nuevos init MP, nullable físicamente hasta backfill. `Payment.expectedAmount` Decimal o monto en unidades menores, según decisión de moneda/precisión; el `amount Float` legado no es un snapshot seguro para igualdad monetaria exacta. No exponer ninguno de estos IDs como prueba de cobro.
- `PaymentPreferenceAttempt`: `id`, `paymentId` FK, `preferenceId String? @unique`, `state` (`CREATING`, `ACTIVE`, `EXPIRED`, `REVIEW`), `expectedAmount`, `expectedCurrency`, `expectedCollectorId`, `createdAt`, `updatedAt`; `@@index([paymentId,state])`. Restricción SQL propuesta `UNIQUE(paymentId) WHERE state IN ('CREATING','ACTIVE')` para un solo intento abierto (Prisma necesita SQL de migración explícito para índice parcial). Una segunda preferencia no borra la historia; `Payment.mpPreferenceId` apunta a la vigente. Si no se necesita historial tras decidir el producto, alternativa mínima es solo columnas en Payment y prohibir segundo init mientras vigente, con riesgo de preferencia creada pero no persistida.
- `mpActualPaymentId` único impide asociar un pago remoto a dos pagos locales. Para múltiples pagos remotos de un checkout, registrar eventos/conflictos en tabla de intentos/auditoría sin sobreescribir el vínculo único; exigir decisión de resolución. `external_reference` remoto apunta a `Payment.id`, pero no es autorización: verificar el resto de invariantes y vinculación de preferencia. Índices/columnas nuevos se crean nullable y no se borran datos antiguos en fase inicial.

## Secuencia y concurrencia

1. Expandir esquema nullable + índices únicos, desplegar lector compatible, **gateway MP apagado para nuevos init** mientras se clasifican históricos. Inventariar por entorno `mpPaymentId` no nulo, status, preferencia y transacciones en vuelo sin exportar PII. No copiar a ciegas: clasificar formato/origen usando datos autorizados; `mpPaymentId` puede contener `stub-*`, preferencia antigua o ID real reescrito por webhook. Migrar solo preferencia demostrada a `mpPreferenceId`; pago real solo tras `Payment.get` firmado/consultado y comprobación completa; desconocidos a cuarentena sin cambio de status. Evitar reescritura destructiva.
2. Init nuevo: bajo exclusión por Payment (lock corto/claim condicional), reservar un intento `CREATING` con monto/moneda/collector congelados y no permitir otro init concurrente. La llamada remota ocurre fuera de transacción larga; persistir `Preference.id` y marcar `ACTIVE` de forma condicional si sigue PENDING y el intento es el mismo. Si la llamada falla, marcar reintentable; si crea preferencia pero falla persistencia, bloquear nuevos init hasta recuperación/manual de ese intento. Para reintento del mismo request usar clave de idempotencia si el endpoint/proveedor la soporta tras validación en sandbox; no asumir que `Preference.create` es idempotente. Responder con la preferencia activa en replay válido, nunca crear una segunda inadvertidamente. Un webhook puede llegar antes de persistir preferencia: guardar para reconsulta durable o devolver error reintentable, jamás confirmarlo por body.
3. Webhook: validar query `data.id` de un solo valor y firma con SDK; exigir tópico payment y coherencia de IDs query/body; `Payment.get({id})` con token de prueba/prod correspondiente. Comparar ID, external_reference, preferencia (si disponible/fiable), monto, moneda, collector esperado y entorno; si falta un atributo requerido, poner en revisión. `action` no participa en el mapeo. Con recurso aprobado y vínculo probado, transacción/`updateMany` condicional `where:{id,status:'PENDING',mpActualPaymentId:null}` más unicidad del ID remoto; si conflicto, releer y registrar discrepancia. Toda carrera de dos eventos/otro flujo se resuelve sin `update` incondicional. En la misma transacción guardar asociación y status, no separar ambas escrituras. Terminales `CONFIRMED`/`FAILED`/`REFUNDED` no se reescriben; cambio real posterior se escala a flujo explícito de reversión/disputa. Evitar marca FAILED por rechazo de un solo intento si hay otro checkout posible.
4. Observabilidad: métricas para firmas inválidas, GET fallido, correlación faltante, atributos discrepantes, duplicados y transiciones conflictivas; IDs opacos para diagnóstico, sin body completo, headers completos ni secreto. Respuestas 5xx reintentables si consulta no se pudo completar y no existe cola durable; 200 solo una vez registrado evento pendiente en cola durable o ignorado verificadamente. Retries supervisados y reconciliación programada de PENDING con acceso autorizado al proveedor, sin atribución por preferencia sola.

## Rollout reversible / contract

- **Preflight humano:** decidir moneda/precisión, identidad de collector, política de reintentos, manejo de FAILED/refunds, autorizar schema y backfill; revisar datos históricos antes de activar MP. No activar split. Migración expand primero, luego backfill verificado, luego código nuevo con feature flag por entorno, luego contract **en cambio posterior** con backup/verificación. No transformar `mpPaymentId` mediante `UPDATE mpActualPaymentId = mpPaymentId`.
- **Filas existentes/in-flight:** durante cambio de versiones, congelar nuevos init MP o usar compatibilidad de doble lectura SOLO para identificar la preferencia legada, nunca para confirmar. Eventos sin snapshot/intent confirmado quedan en revisión manual. Conservar fila, estado y antigua referencia intactos para auditoría; transacciones PENDING antiguas no pasan a CONFIRMED automáticamente. Probar que no haya procesos antiguos escribiendo `mpPaymentId` antes de activar flujo nuevo.
- **Rollback app:** desactivar nuevos init/webhooks MP y volver a versión segura/stub solo para tráfico de prueba; **no** desplegar la ruta vieja MP que confirma por body. Retener columnas, intentos y eventos para auditoría (rollback de comportamiento no exige borrar esquema). Reconciliar pendientes antes de reabrir checkout. **Rollback schema**, si imprescindible y autorizado por separado: después de export/backup y comprobar que ninguna versión depende de columnas nuevas, retirar índices/tablas/columnas añadidas; nunca restaurar el valor legado sobre un ID real ni perder IDs de pagos confirmados. La contracción es deliberadamente posterior y no automática.

## Riesgos y límites

- Una comisión aritmética local no mueve dinero: Marketplace/split y `OperatorProfile.mpAccountId` quedan fuera; antes de cualquier transferencia se necesita contrato específico y pruebas del proveedor. `Payment.FAILED` terminal actual puede colisionar con reintentos; no decidir comportamiento irreversible sin producto.
