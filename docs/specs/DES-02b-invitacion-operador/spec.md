# DES-02b — Contrato seguro

- `POST /api/admin/operator-invitations`: sesión vigente y ADMIN actual en DB, JSON estricto `{ "phoneNumber": "+..." }` E.164 sin espacios. Crea token de 32 bytes CSPRNG codificado en 64 hex minúsculas; guarda exclusivamente SHA-256 único, emisor FK, fecha y vencimiento +24h. Respuesta 201 `{token, expiresAt}` con `Cache-Control: no-store`; no existe GET ni envío automático. 401 sin sesión vigente, 403 sin rol, 400 body inválido, 429 límite, 500 interno saneado. No revela existencia de usuario destinatario.
- `POST /api/operator/invitations/redeem`: sesión Better Auth vigente reconsultada en DB por ID; usuario actual CLIENT, `phoneNumberVerified=true`, número exacto E.164 de invitación. Body estricto `{ "token": "<64 hex>" }` sin campos de rol/ID/teléfono. Digest SHA-256, vence a las 24h, consume condicional si no consumido y aún vigente; update de usuario CLIENT→OPERATOR en misma transacción. Responde 200 `{redeemed:true}`; token inexistente, vencido, usado o teléfono distinto siempre 400 `INVALID_INVITATION` mientras el actor sea elegible. 401 sesión ausente/revocada/vencida, 403 actor inelegible, 429 cuota. Ante fallo DB, rollback y 500 genérico.
- Las rutas Better Auth no pueden aceptar `role` desde cuerpo público (`additionalFields.role.input=false`); rol de sesión cacheado no autoriza emisión/canje.
- Cuotas DB: 20 intentos de emisión/ADMIN por ventana móvil de 24h, 10 intentos de canje/CLIENT por ventana móvil de 1h. El bloqueo `FOR UPDATE` de la fila User serializa contador, evento y mutación para ese actor incluso entre procesos. El evento de límite cuenta como denegación pero no prolonga permanentemente la ventana. No usar memoria local ni Redis como autoridad. Reintentar después del vencimiento de la ventana; emisión repetida produce nuevos tokens, el anterior sigue válido hasta consumirse/vencer; resguardar cada token y revocarlo manualmente en DB si se extravía (no hay panel).
- `OperatorInvitationEvent` con actor FK, acción, resultado, motivo genérico, instante; sin token/hash/teléfono. Eventos de sesión inexistente/revocada no tienen actor confiable y no se guardan. Eventos de fallo DB pueden revertirse con la transacción: errores operacionales requieren observabilidad de infraestructura separada, sin registrar cuerpos de petición.
- El primer ADMIN y el rollback son operaciones humanas fuera del API (`docs/runbooks/`). La migración crea dos tablas aditivas y no modifica roles de usuarios existentes.
